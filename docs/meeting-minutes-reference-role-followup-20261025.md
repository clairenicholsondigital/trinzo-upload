# Direct references, separate accounting and contained requirements

Status: isolated research; no production integration or automatic merge is qualified. The live app and all 59 saved drafts remain unchanged.

## Implemented

The new research contract uses server-owned immutable evidence fields instead of asking the model to copy quotes, field labels and long record hashes. One short request token binds the response to a frozen packet containing both exact originals, the selected existing survivor, source context and the global inventory. Tests reject another token, changed packets, unknown or cross-field references, missing checks and ambiguous source identifiers. Record hashes remain checked server-side.

Source support and retention are now separate accounting structures. Source requests always cover BOTH originals, including the survivor. Retention requests cover only the discarded original. Exact self-retention cannot excuse missing source support.

Source support distinguishes an assigned commitment, a required component within a commitment, unsupported wording and uncertainty. The relationship judgment separately distinguishes the same obligation, a discarded requirement already contained in the survivor, distinct work, partial overlap and uncertainty. A required component does not have to have been assigned as an additional standalone action. Separate methods, occurrences, communications, purchases, fitting, reviews and approvals are not collapsed merely because they form a workflow.

The model is not authorized to edit. Every accepted response is materialized back through the existing research evidence/ownership validator and unchanged deterministic coverage diagnostics. Reviewer edits, warnings, quantities, conditions, timing/history, recipients and occurrence identity remain protected. Positive role judgments do not bypass those safeguards.

## Qualification

40 fresh requests to the existing Microsoft endpoint, one attempt each, concurrency at most two:

- Eight real-data checks: Allotment and Eakin, both survivor choices and both inventory orders.
- The previous 26 blinded synthetic cases.
- Six new held-out requirement/independent-work contrasts involving notices, registers and release notes (three positive, three negative).

Expected verdicts and descriptive fixture IDs were hidden. All 40 transports returned HTTP 200. No provider response was replayed as a fresh call. There were no AI reference-repair calls or semantic-veto retries in this phase. Real transcript-bearing requests and replies remain private.

The emitted prototype used short source aliases alongside the canonical unit IDs already present in app records. Six real-data responses selected the canonical source IDs rather than those aliases; the strict wire check initially rejected them. Their mapping to the exact same text source units was unique and lossless. A recorded offline conversion changed only reference identifiers, not any source/retention verdict, role, relationship, reason or request binding. Original replies and initial failures remain preserved. Unknown or ambiguous references cannot be translated. A collision regression caught and corrected an ambiguity-handling bug before final assessment.

The preparer now uses the canonical app source IDs directly, with explicit speaker-metadata references and collision checks. This removes the unnecessary alias layer from future packets. The future packet naming convention was validated locally; no extra model run was claimed for that local preparation change. The captured responses already demonstrate the provider's use of canonical IDs.

Final accounting after exact canonical-reference resolution: **40/40 structurally valid assessments**, compared with 34/40 before that deterministic wire correction. All source checks for both originals are present; none is inferred from self identity. 99 relevant local regressions pass. Hash verification confirms all 59 library rows and the environment unchanged; deployed revision remains a1c3960901f111a84857b83ab9580b7ec0a43c68.

The earlier content-within-deliverable control now passes as a required component rather than being rejected for lacking a separate assignment. The new held-out cases show that this distinction is not limited to letters.

The remaining positive-control failure concerns semantically equivalent display-driver wording. The model's stated reason is that the instruction is not worded identically to the source/survivor. The veto is retained; no prompt retry converted it into an approval. This establishes a remaining conservative paraphrase limit, not a general explanation of all duplication.

Eakin is also a useful remaining warning: the model accepts both dependency phrasings, including the less explicit one. Its positive judgment alone must not permit the app to drop an explicit qualification or resolve timing. Keep the fuller dependency and the existing timing guard in any later scoped experiment.

## Remaining integration work

The feasibility questions in this batch now have useful answers: direct references avoid quote-copy failures; separate accounting covered both originals in every completed response; contained requirements can be distinguished from separate work on these new examples. This is one bounded sample, not a guarantee of zero future errors or a production repetition fix.

The next implementation should be a small integration for source-proved contained content in one existing deliverable, starting with the untimed class. It needs direct proof against the exact final survivor, independent challenge, immutable recovery/lineage and explicit qualification of any operation/container/effective-date exceptions. Existing guard failures are not blanket permission to bypass them. Connect the new evidence contract to the existing clause/proof/receipt contracts, then verify admission, save/reload, export and recovery before deployment.

Keep Eakin's dependency/timing scope and broader duplicate-task classes outside that first integration. Group-to-atomic materialization remains a separate app/Microsoft protocol issue. A fresh five-generation comparison belongs after a bounded production candidate is qualified, not before these integration checks.
